# Benchmark Golden Snapshots

Checked-in performance baselines used by the Phase 21 regression CI
(`.github/workflows/bench-regression.yml`). Every PR touching
`src/soma/memory/**`, `src/soma/io/**`, or `benchmarks/**` runs the
matching harness and diffs the output against these JSON files via
`scripts/check_bench_regressions.py`.

Tolerances (default):
- latency / disk metrics: ±20%
- recall / MRR / NDCG: ±5%

## Files

| File | Source harness | Command that regenerates it |
| --- | --- | --- |
| `scale_vs_chroma.json` | `benchmarks/run_scale_vs_chroma.py` | `python -m benchmarks.run_scale_vs_chroma --json-out benchmarks/golden/scale_vs_chroma.json --points 1000 5000 20000` |
| `retrieval.json` | `benchmarks/run_retrieval.py` | `python -m benchmarks.run_retrieval --json-out benchmarks/golden/retrieval.json` |
| `backend_matrix.json` | `benchmarks/run_backend_matrix.py` | `python -m benchmarks.run_backend_matrix --n 5000 --smoke --out /tmp/bm.md` then copy the sidecar `/tmp/bm.json` |

## Provenance (2026-04-16, initial commit)

All three snapshots were generated by running the harnesses locally on
the same machine (Windows 11, Python 3.12) against `main` at commit
`d54621e`. The full live runs include sentence-transformers load, FAISS
index construction, and (for `scale_vs_chroma.json`) a fresh Chroma
PersistentClient at each scale point.

- `scale_vs_chroma.json` — full matrix: {1K, 5K, 20K} × {soma-flat,
  soma-hnsw, chroma}. Nine rows. About 12 min wall-clock.
- `retrieval.json` — all three comparisons (sbert headline + TE graph
  ablation + sbert graph ablation). Six rows. About 3 min wall-clock.
- `backend_matrix.json` — smoke path only (InProcFlat at N=5000). One
  row. About 5 seconds. CI uses `--smoke` to stay under the 10-minute
  budget; this keeps the baseline aligned with CI.

The initial snapshots are deliberately *tolerant* starting lines. The
first few nightly runs will likely surface run-to-run variance that
exceeds ±20%; operators should re-tune thresholds or widen goldens by
re-running + committing the new JSON, not by disabling the check.

## Regenerating

**Run locally, commit the new JSON.** The checker is not self-healing —
it will never update a golden unless the golden file is missing (in
which case it bootstraps from `--current`). To relax / refresh a
golden after an intentional perf change:

```bash
python -m benchmarks.run_scale_vs_chroma \
    --json-out benchmarks/golden/scale_vs_chroma.json \
    --points 1000 5000 20000
git add benchmarks/golden/scale_vs_chroma.json
git commit -m "bench: refresh scale_vs_chroma golden after <change>"
```

## Markdown-seed fallback

If the harnesses can't run in your environment (e.g. faiss-cpu /
chromadb / sentence-transformers aren't installable), the fallback is
to seed the JSON by hand from the numbers in `benchmarks/reports/*.md`.
Mirror the dataclass shape produced by each harness (see their
`asdict(row)` call sites). This is a bootstrap convenience only — the
long-term source of truth is a live harness run.
