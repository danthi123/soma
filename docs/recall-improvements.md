# Beating Chroma / Pinecone on Recall — Research Agenda & Status

## The problem

SOMA currently *ties* Chroma/Pinecone/LanceDB on recall when using
the same embedder — and it ties them by mathematical construction:
all three compute cosine over identical sbert vectors, so Recall@k
is identical modulo ordering ties (see `benchmarks/reports/retrieval.md`
and the LoCoMo evaluation in `paper-draft.md` §3.4). Winning on
mechanics (store time, disk, HNSW latency) doesn't move recall.

To *beat* peer systems on recall, SOMA must offer something they
don't — either a different retrieval pipeline, or a retrieval-time
signal that pure cosine can't reach.

## Shipped (2026-04-16)

Both are opt-in kwargs on `MemoryLayer.retrieve()`. Default retrieve
stays pure cosine for backward compat and for matching peer systems
when that's what the caller wants.

### 1. Hybrid search (BM25 + vector)

```python
hits = mem.retrieve("query", k=5, hybrid_alpha=0.3)
# alpha=0.0 → pure BM25; alpha=1.0 → pure cosine; 0.3-0.5 typical.
```

- Pure-Python BM25-Okapi implementation in `soma.memory.bm25`
  (no extra deps).
- Lazy index build, versioned against `_step` so stores invalidate
  automatically.
- Union-candidate pooling + max-normalised score blend.
- Handles terminology-rich queries where sbert's sub-word tokens
  smear the meaning (proper names, domain jargon, numeric IDs).

### 2. Cross-encoder re-ranking

```python
from soma.memory.rerank import CrossEncoderReranker
mem.attach_reranker(CrossEncoderReranker())  # lazy model load

hits = mem.retrieve("query", k=5, rerank_top_n=20)
# over-fetch 20 cosine candidates, re-score with cross-encoder,
# return top-5 of the re-ranked list.
```

- `Reranker` protocol is one method: `score(query, candidates) -> list[float]`.
- Default: `cross-encoder/ms-marco-MiniLM-L-6-v2` (23 MB, ~5-10 ms
  per candidate on CPU). Lazy-loaded.
- Original pre-rerank score preserved in
  `metadata["_pre_rerank_score"]` for analysis.

### 3. Composition

```python
hits = mem.retrieve(
    "query", k=5, hybrid_alpha=0.3, rerank_top_n=20
)  # hybrid pool → cross-encoder rerank → top-5
```

### Measured lift

See `benchmarks/reports/recall_boost_locomo.md` (generated by
`python -m benchmarks.run_recall_boost`). Every row uses the same
sbert embedder and the same LoCoMo corpus (5,882 turns, 1,986
questions with gold evidence). The baseline row is exactly what
any vector DB with the same embedder achieves on the same corpus.

## Not-yet-shipped — ranked by expected impact

### 4. In-index metadata filtering at retrieve time

Chroma supports `where` clauses during retrieve that filter candidates
by metadata *before* ranking. SOMA requires post-filtering, so on
heavily-filtered queries we're slower and can miss candidates that
a pre-filter would have caught inside the top-N. Matching parity here
is a latency + ergonomics win, not a recall win — but "ergonomics
parity with Chroma" is table stakes for drop-in replacement.

**Shape:** `mem.retrieve(query, k=5, where={"user_id": "alex"})` →
pre-filters indexable metadata fields via a secondary posting list.

### 5. Query expansion via LLM

Under-specified queries benefit from rewriting into a set of
variants whose top-k are unioned. Cheap with the LLM already in the
pipeline.

**Shape:** optional `QueryRewriter` passed to `RAGSession` that
produces N variants, runs retrieve on each, merges by RRF
(reciprocal rank fusion). Expected lift: +3-8% R@5 on hard queries.

### 6. Multi-vector / ColBERT-style retrieval

Instead of one pooled embedding per entry, store per-token
embeddings. At retrieve time, for each query token find the max
similarity against all doc tokens (MaxSim operator) and sum — this
captures local alignment that a single pooled vector loses.

**Impact:** BEIR benchmarks show +10-20% R@k over pure bi-encoders.
**Cost:** 5-10× disk (N × seq_len × dim instead of N × dim);
retrieve latency proportional to total tokens unless a smart index
is built. Bleeding edge but the biggest possible single jump.

**Shape:** new `store_multivector(text)` that embeds per-token,
plus a `retrieve_multivector(query, k)` that implements MaxSim over
the stored per-token matrices.

### 7. Learned graph re-rank (activate SOMA's substrate)

SOMA's graph plasticity ships but doesn't move Recall@3 on synthetic
small corpora (ablation in `paper-draft.md` §4.1). Open question:
does a different consolidation objective (contrastive / classification
over stored topic clusters) produce a graph signal that actually
lifts recall above cosine?

**Impact:** unknown — currently 0. If it works, unique to SOMA.
**Cost:** research project. 2026-Q3 target; not v1.

### 8. Importance-weighted embeddings (retrieval-aware fine-tune)

Fine-tune a small projection layer on top of sbert that is trained
*on the user's corpus + their retrieval history* to maximise the
Recall@k seen on their actual query distribution. Per-user model =
local privacy + adaptation.

**Impact:** +3-10% R@5 typical in domain-adaptive IR literature.
**Cost:** one training pass per user (minutes on CPU for small
corpora); periodic re-train as corpus grows.

### 9. Summarization layer (Mem0-like, optional)

For each new entry, optionally generate an LLM-extracted fact
sentence, store it alongside raw text with a `summary=True` flag.
Retrieve queries both layers; blend. Helps when the raw text is
conversational and the actual fact is buried.

**Impact:** can help a lot for chat-log corpora; neutral-to-negative
for already-factual docs.
**Cost:** one LLM call per store = slow + expensive.
**Ergonomics:** offer it as `mem.store(text, summarize=True)` or a
periodic batch `mem.summarize_batch()`.

## Other dimensions where peer systems beat SOMA today

Beyond recall, the feature gap that matters for "drop-in" status:

| Gap | Status | Priority |
| --- | --- | --- |
| In-index metadata filtering (§4) | missing | high (P1) |
| Distributed multi-node scale | single-process | low (P3) — not the positioning |
| Multi-modal (image, audio embeddings) | text-only API | medium (P2) |
| Managed/hosted multi-tenant | self-host only | out of scope for v1 |
| Web UI / dashboard | CLI inspector only | medium (P2) |
| Metrics / Prometheus | not exposed | low (P3) |
| Streaming ingest (server-sent updates) | not exposed | low (P3) |

The managed-hosting line is deliberate — SOMA's positioning is
local-first (`docs/positioning.md`). We don't intend to match
Pinecone/Weaviate Cloud on hosted-tenant story; we intend to beat
them on "your memory, your disk."

## When will SOMA *actually* beat peer systems on recall?

Today's shipped path: hybrid + rerank gets any strict improvement
the caller opts into. `benchmarks/reports/recall_boost_locomo.md`
quantifies it. That alone makes SOMA strictly ≥ Chroma/LanceDB on
recall when the caller toggles the kwargs, because the peer systems
don't have equivalent built-in.

Medium-term path (§4, §5): in-index metadata filters + query
expansion close the ergonomics + hard-query gap.

Long-term path (§6, §7, §8): multi-vector and learned re-rank are
the routes to Recall@k deltas that no cosine-based system can reach
regardless of its embedder.

## How to measure honestly

The only honest way to claim "SOMA beats X on recall" is:

1. Fix the embedder (sbert, or any comparable encoder).
2. Fix the corpus (LoCoMo, BEIR slices, user's own data).
3. Fix the metric (Recall@k, NDCG@k).
4. Compare *pipelines* on those axes.

The benchmark harness does this. `benchmarks/run_recall_boost.py`
adds the strategy axis. Extending it to compare hybrid-SOMA vs
hybrid-Qdrant etc. is a ~100-line adapter addition per peer; those
are pre-scoped in `paper-draft.md` §5 when time and (sometimes) API
keys allow.
